# 문서 9종 판정 기준

각 문서의 **최소 입력 조건**(이게 없으면 `NOT_READY`), **변경 신호**(이게 생기면 `UPDATE`), **Deprecation 조건**을 정의한다.
작성 양식과 작성 방법은 이 문서의 범위가 아니다.

---

## PRD

**목적** — 무엇을, 누구를 위해, 왜 만드는지에 대한 합의.

**최소 입력 조건** (모두 필요)

- 해결하려는 문제가 한 문장으로 서술될 수 있다.
- 대상 사용자가 식별되었다.
- 제품이 성공했는지 판단할 기준이 하나라도 있다.

**`NOT_READY` 예시** — "뭔가 자동화 도구를 만들어 보자" 수준의 아이디어만 있고 대상 사용자나 성공 기준이 없는 상태.

**변경 신호** — 대상 사용자 변경, 문제 정의 변경, 성공 지표 변경, 범위의 명시적 추가·축소.

**Deprecation 조건** — 제품 자체가 중단되었거나 다른 제품에 흡수됨.

---

## Requirements

**목적** — 무엇을 충족하면 완료인지에 대한 검증 가능한 목록(기능/비기능/수용 기준).

**최소 입력 조건**

- PRD 또는 그에 상응하는 목표·범위 합의가 존재한다.
- 사용자가 수행할 동작이 하나 이상 구체적으로 식별되었다.

**`NOT_READY` 예시** — 목표만 있고 어떤 동작을 지원할지 정해지지 않은 상태. 이 경우 PRD를 먼저 처리한다.

**변경 신호** — 기능 추가·삭제, 수용 기준 변경, 성능·보안·가용성 등 비기능 목표 변경, 범위 변경, 사용자 흐름 변경.

**Deprecation 조건** — 해당 요구사항이 속한 기능이 제거되었거나, 요구사항 문서가 더 세분화된 문서로 대체됨.

---

## ADR

**목적** — 하나의 결정에 대한 시점 기록: 맥락, 검토한 대안, 결정, 결과.

**최소 입력 조건** (모두 필요)

- 결정이 **실제로 내려졌다**. (검토 중인 사안은 ADR이 아니다)
- 검토된 대안이 하나 이상 있었다.
- 결정의 맥락(제약, 트레이드오프)이 서술될 수 있다.

**ADR을 쓰지 않는 경우**

- 대안이 없었던 자명한 선택.
- 아직 결정되지 않은 사안. (열린 질문으로 남기고 결정 후 작성)
- 되돌리기 쉽고 영향 범위가 좁은 선택.

**변경 신호** — 대안이 있었고 되돌리기 어려운 새 결정. 기존 결정의 번복.

**`UPDATE` 금지** — ADR은 수정하지 않는다. 결정이 바뀌면 새 ADR을 쓰고 기존 ADR에 `Superseded by <새 ADR>`만 표시한다. 상태 표기 추가 외의 내용 수정은 하지 않는다.

**Deprecation 조건** — 결정 대상이 제품에서 사라짐. 이 경우도 삭제하지 않고 상태만 표시한다.

---

## System Architecture

**목적** — 시스템 경계, 구성요소, 외부 연동, 런타임·배포 토폴로지.

**최소 입력 조건**

- 시스템 경계(무엇이 우리 시스템이고 무엇이 외부인지)가 식별되었다.
- 구성요소 또는 외부 의존 시스템이 둘 이상 식별되었다. (단일 프로세스에 외부 연동이 전혀 없다면 아직 `NOT_READY`)

**변경 신호** — 구성요소 추가·제거, 외부 시스템 연동 추가·제거, 통신 방식 변경(동기↔비동기, 프로토콜), 배포 단위·환경 변경, 인증·경계 보안 구조 변경.

**Deprecation 조건** — 시스템이 폐기되었거나 전면 재설계로 문서 전체가 대체됨.

---

## Application Architecture

**목적** — 애플리케이션 내부 레이어, 모듈 구성, 의존성 방향 규칙, 공통 관심사 처리 방식.

**최소 입력 조건**

- 레이어링·모듈 구조가 결정되었거나 코드에 실제로 존재한다.
- 모듈 간 의존성 규칙을 서술할 수 있다.

**`NOT_READY` 예시** — 파일 몇 개만 있고 구조에 대한 결정이 없는 초기 상태.

**변경 신호** — 레이어 추가·제거, 모듈 경계 변경, 의존성 방향 규칙 변경, 공통 관심사(인증, 로깅, 트랜잭션, 에러 처리) 처리 방식 변경, 프레임워크 교체로 인한 구조 변화.

**Deprecation 조건** — 해당 애플리케이션이 제거되었거나 구조가 전면 교체됨.

---

## Data Architecture

**목적** — 데이터 모델, 소유권, 저장소, 흐름, 보존 정책.

**최소 입력 조건**

- 영속 데이터 또는 저장소가 존재하거나 결정되었다.
- 핵심 엔티티가 하나 이상 식별되었다.

**`NOT_APPLICABLE` 조건** — 영속 데이터를 다루지 않는 프로젝트(순수 계산 라이브러리, stateless 변환 도구 등).

**변경 신호** — 스키마 변경, 저장소 추가·교체, 데이터 흐름·동기화 방식 변경, 데이터 소유권 이동, 보존·삭제·개인정보 처리 정책 변경.

**Deprecation 조건** — 저장소나 데이터셋이 폐기됨.

---

## Tech stacks

**목적** — 사용하는 언어, 프레임워크, 라이브러리, 인프라와 그 버전·선택 이유.

**최소 입력 조건**

- 기술 선택이 하나 이상 확정되었다.

보통 가장 먼저 작성 가능해지는 문서다. 의존성 선언 파일이나 설정 파일이 있으면 최소 입력 조건은 충족된다.

**변경 신호** — 기술 추가·제거·교체, major 버전 변경, 런타임·인프라 변경, 빌드·배포 도구 변경.

**Deprecation 조건** — 프로젝트 종료. 개별 기술이 빠지는 것은 `UPDATE`다.

---

## Wireframe

**목적** — 각 화면의 구성 요소와 배치.

**최소 입력 조건**

- UI가 있는 제품이다.
- 화면이 하나 이상 식별되었고, 그 화면에 표시될 정보·조작 요소를 서술할 수 있다.

**`NOT_APPLICABLE` 조건** — CLI, 라이브러리, 백엔드 전용 서비스, API 전용 제품.

**변경 신호** — 화면 추가·삭제, 화면 내 정보·조작 요소 변경, 내비게이션 구조 변경.

**Deprecation 조건** — 해당 화면이 제거되었거나 재설계로 대체됨.

---

## Storyboard

**목적** — 사용자가 목적을 달성하기까지 지나가는 화면·단계의 순서.

**최소 입력 조건**

- 주요 사용자 시나리오가 하나 이상 정의되었다.
- 그 시나리오에서 연결되는 화면 또는 단계가 둘 이상 식별되었다.

**`NOT_READY` 예시** — 화면은 식별되었지만 사용자가 어떤 순서로 쓰는지 정해지지 않은 상태. Wireframe을 먼저 처리한다.

**`NOT_APPLICABLE` 조건** — 사용자 상호작용 흐름이 없는 제품.

**변경 신호** — 사용자 흐름 변경, 단계 추가·삭제·순서 변경, 진입점·이탈점 변경, 예외·실패 흐름 변경.

**Deprecation 조건** — 해당 시나리오를 더 이상 지원하지 않음.

---

## 처리 순서

조치 대상이 여러 개면 의존 관계 순서로 진행한다.

```
Tech stacks → PRD → Requirements → ADR → System Architecture
→ Application Architecture → Data Architecture → Wireframe → Storyboard
```

상위 문서가 `NOT_READY`면 그에 의존하는 하위 문서도 대체로 `NOT_READY`다. 이 경우 가장 상위의 막힌 지점 하나만 "다음 조건"으로 보고한다.
